## 学习记录

### 与 Octo-Ad-Issue-Dispatcher 机制对比
小胡让我学习 Dispatcher 的监控通知机制，对比差异：

**Dispatcher 机制：**
- 事件驱动为主：issue assign → octo-daemon 自动拉起 agent task → 秒级响应
- 定时轮询兜底：每小时（工作日10-20点）做自愈+异常检测+排队派发
- 通知走脚本：notify-card.sh 发结构化卡片，不同场景不同颜色

**我的机制：**
- 纯定时轮询：每3分钟跑 issue_poll.py 检测变化
- 无事件驱动：全靠轮询抓事件
- 通知在 agent run 里直接发文本

**核心差异：**
1. 响应速度：他秒级，我最快3分钟
2. 轮询定位：他兜底自愈，我主力抓事件
3. 自愈能力：他有记账核对+异常检测，我没有
4. 通知格式：他走脚本发卡片，我裸发文本
5. 职责：他管技术派发+流程把控，我管需求跟踪+通知提需人

**第二轮学习（Dispatcher 补充）：**

Dispatcher 补了三个点：
1. 通知卡片化本质是信息架构——颜色编码让提需人一眼知道"要不要行动"，不是好看问题
2. 状态持久化——他有 dispatched-issues.md 记账，我已有 snapshot 机制覆盖大部分，但缺"已通知事件"去重记录
3. 心跳时间戳——每次轮询写时间戳到文件，超10分钟没更新就告警，成本极低

优先级排序：
1. 心跳时间戳（防瞎掉，最高优先）
2. 通知去重记录（防重复通知）
3. 通知卡片化（提体验）

**当晚已落实（18:23）：**
- ✅ 心跳时间戳：issue_poll.py 每次运行写 state/poll-heartbeat.txt（Unix 秒级时间戳）

**可借鉴：** 事件驱动机制（接 event webhook 提响应速度）、通知卡片化（格式统一）
