# 需求审核 Skill

## 触发条件

当产品同事提交需求描述时触发。输入物为自然语言需求描述（不限定格式，口头描述、一段话、半结构化文本均可）。

## 核心流程

```
需求描述输入
    ↓
Step 1: 需求分类
    ↓
Step 2: 按类别检查信息完整性
    ↓
Step 3: AdMonitor知识粗判（交叉校验）
    ↓
Step 4: 输出结构化审核报告（含工程风险提示）
    ↓
回到产品确认/补充
    ↓
梳理清楚后提给技术
```

## Step 1 — 需求分类（5类）

1. **Bug** — 现有功能不符合预期，需要修复。关键词："不对""错了""功能坏了""之前好好的现在不行了"
2. **数据异常** — 数据缺失/异常/口径不一致。系统功能没坏，但数据看起来不对。可能是口径差异、过滤逻辑差异、地域解析差异等。关键词："UV对不上""数据突然少了""和界面显示不一致""和媒体那边对不上"
3. **新功能** — 全新功能开发，系统目前不具备的能力。包括IVT规则升级、新自动化流程等。关键词："能不能加""希望支持""新增""升级"
4. **二次开发（跑数需求）** — 现有界面功能和DMS无法支持产品跑数，或跑数周期过长、范围较大，需要研发支持。一般有具体客户提出的硬数据需求。关键词："跑不了""DMS不支持""跑数太慢""客户要的数据出不来"
5. **其他（含咨询）** — 不属于以上任何一类，或产品同事来咨询"能不能做""为什么数据是这样的"

分类判断依据：优先看关键词 → Bug和数据异常的区别：Bug是功能坏了要复现，数据异常是数据看着不对要对口径 → 无法明确分类标"其他"

## Step 2 — 按类别检查信息完整性

### 通用必填项（5项，所有类别都要检查）

| 信息项 | 说明 |
|--------|------|
| 需求描述 | 具体要做什么，含起因 |
| 需求方 | 谁提的？哪个客户/哪个团队？ |
| 期望结果 | 要解决什么问题，做完什么样算成功 |
| 涉及产品线 | ADM / TVM / 通用 |
| 涉及系统层面 | 见下方清单（选1-3个） |

涉及系统层面清单（按架构视角分，ADM和TVM分开列）：

**ADM系统层面：**

1. **界面** — 包括：
   - 数据洞察（Dashboard / 实时数据 / 基础数据 / 到达效果 / 地域分析 / 人群分析 / 个性分析 / 转化效果 / 异常流量）
   - 活动管理（活动 / 点位 / 排期 / 监测代码部署）
   - 多维钻取
   - M+任务定制
   - 报告归档
   - 账号 / 权限管理
2. **API/MCP** — 数据接口、MCP维护
3. **大数据** — Terran收数 / ETL数据清洗 / SIVT计算 / DR/Panel/Universe / M+计算 / 实时计算
4. **SDK** — Android/iOS秒针SDK
5. **SNAP监拍**
6. **Content Tracking** — 剧目监测，only for KA
7. **实验室/云手机**
8. **其他**

**TVM系统层面：**

1. **界面** — 包括：
   - 数据洞察（Dashboard / 实时数据 / 基础数据 / 到达效果 / 地域分析 / 人群分析 / 个性分析 / 转化效果 / 异常流量）
   - 活动管理（活动 / 点位 / 排期 / 监测代码部署）
   - 多维钻取
   - M+任务定制
2. **API/MCP** — 数据接口
3. **大数据** — Terran收数 / ETL数据清洗 / SIVT计算 / DR/Panel/Universe / M+计算 / 实时计算
4. **其他**

TVM没有：SDK、SNAP、Content Tracking、实验室/云手机、报告归档、账号/权限管理

注：界面子模块拆分较粗，后续迭代优化。

### 短路逻辑

- 只有"需求描述"+"期望结果"两项缺失才直接打回
- 其他缺失项（需求方/涉及产品线/涉及系统层面/优先级）标记提醒但不打回，PM可以自己补

### 各分类专属必填项

**Bug类：**
- 复现步骤：具体怎么触发
- 预期结果：应该是什么样
- 实际结果：现在是什么样
- 影响范围：影响哪些功能/客户/数据
- 出现时间：何时开始
- 环境信息：平台类型（pc/mb/pm）、账号权限、测试/生产环境、涉及活动ID

**数据异常类：**
- 涉及客户
- 指标名称：哪个指标的数据有问题
- 期望值vs实际值
- 时间范围：哪个时间段的数据
- 是否已自查GAP

**新功能类：**
- 功能目标：做完之后什么算成功
- 功能点描述：具体要做什么，拆成可执行的功能点
- 使用场景：谁用，什么场景下用
- 验收标准（选填）：skill引导产品思考"你觉得做完什么样算成功"，不硬要
- 是否有竞品参考（选填）

**二次开发（跑数需求）类：**
- 具体客户：哪个客户提的
- 数据需求：要跑什么数据，哪些指标/维度
- 现有能力瓶颈：界面/DMS哪里不支持，跑不了还是太慢还是范围不够
- 数据量级：大概多大数据量
- 期望周期：多久跑一次，每次多长时间能接受

**其他（含咨询）类：**
- 列出已获取的信息
- 标注"需进一步沟通"或给出初步回答/指路

## Step 3 — AdMonitor知识粗判

分类和信息完整性检查通过后，自动用AdMonitor知识库做交叉校验：
- 需求提到的指标是否存在、定义是否正确（查 references/admonitor-metrics.md）
- 需求提到的API/接口是否支持（查 references/admonitor-api-capability.md）
- 需求提到的字段是否存在、取值是否合法（查 references/admonitor-fields.md）
- 是否有已知约束冲突（查 references/admonitor-constraints.md）

粗判结果作为审核报告的一个section输出，标记"知识参考，非最终判断"。

按需求分类按需引用对应知识文件，不全量加载。

## Step 4 — 工程实施风险提示（条件触发）

当需求信息足够详细（到了功能点/接口层面）时，自动触发工程风险维度检查。信息不够时跳过，不硬审。

5个维度（详见 references/engineering-risk-checklist.md）：
1. 界面回显对齐
2. 权限适配
3. 数据逻辑对齐
4. 异步任务工程风险
5. 边界场景

有风险点就写进报告，没有就不写，不强制。

## 新增字段 — 建议技术方向

分类完成后，根据需求内容初步判断技术方向（前端/后端/大数据/MCP/端侧/SDK），辅助分发但不做最终决定。最终分给谁由技术负责人判断。

对照研发scope的初步映射：
- 前端/后端 → 吕金果（二次分配黄春波、李晴晴）
- 大数据 → 张成（二次分配：Terran收数董文菁、ETL/实时于长亮、CT陈龙、SIVT杨春雪、DR/panel陈鹏、TVM吴坤城）
- MCP/lite/海外 → 赵思捷
- 端侧 → 周康平
- SDK → 张乾（Android）、王立涛（iOS）

## 输出格式

```
【需求审核报告】

需求分类：[Bug/数据异常/新功能/二次开发（跑数需求）/其他]
审核结论：[通过 / 需补充 / 需沟通]
建议技术方向：[前端/后端/大数据/MCP/端侧/SDK/待定]
涉及产品线：[ADM/TVM/通用]
涉及系统层面：[列出]

—— 通用信息检查 ——
✅ 已提供：[列出]
❌ 缺失项：[列出，附补充提示]
⚠️ 模糊项：[列出，附追问建议]

—— 分类专属信息检查 ——
✅ 已提供：[列出]
❌ 缺失项：[列出]
⚠️ 模糊项：[列出]

—— AdMonitor知识粗判 ——
[指标/API/字段/约束校验结果，标记"知识参考，非最终判断"]
[如无相关项则写"本需求未涉及已入库的系统知识，跳过粗判"]

—— 工程实施风险提示 ——
[条件触发，有则列出风险点，无则写"需求信息未达工程评估粒度，跳过"]

—— 建议下一步 ——
[补充哪些信息 / 可以进入技术评估 / 需先沟通明确]
```

## 注意事项

- 审核目标是帮产品梳理清楚需求，不是替产品做决定
- 审核报告回到产品确认，产品说了算
- 技术细节确认留给技术，skill不越界做专业判断
- AdMonitor知识粗判标记为"参考"，不是权威判断
- 工程风险提示是条件触发，信息不够不硬审
- 分类的目的是确定需要补什么信息，不是为了贴标签
- 界面子模块拆分较粗，后续迭代优化
